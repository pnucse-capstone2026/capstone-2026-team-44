# Decision Layer — 팀원용 개요

`feat/scoring` 브랜치가 무엇을 왜 만들었는지 정리한 문서다.

이 모듈을 처음 보는 사람이 읽어도 이해할 수 있도록 **개념부터 설명한다.** 이미
아는 부분은 건너뛰어도 된다. 세부 근거는 ADR-021~027(`docs/DECISION_LOG.md`)과
`docs/EVALUATION_PROTOCOL.md`에 있고, 이 문서는 그 위를 걷는 지도다.

**30초 요약**

| | 이전 | 이후 |
|---|---|---|
| 점수 | 손으로 정한 가중합 | 데이터로 학습한 **확률** |
| 선택 | 고정 Top-K | Top-K + 근사 보장 + 선택적 예산 + recall 보장 |
| 근거 | "왜 20점인가?" 답 없음 | 코퍼스에서 학습, 부호까지 검증 |
| 평가 | 지표 계산 코드 없음 | Recall@K / MAP@K / NDCG@K + 비교군 4종 |

---

## 1. 이 모듈이 왜 필요한가

### 1.1 우리가 푸는 문제

크롤러가 웹 애플리케이션을 훑으면 **검사할 후보가 수십~수백 개** 나온다.
후보 하나는 `(입력점, 취약점 유형)` 쌍이다. 예를 들면:

```text
GET /product?id=   에 SQL Injection이 있는가?
GET /product?id=   에 Reflected XSS가 있는가?
GET /search?q=     에 SQL Injection이 있는가?
...
```

전부 깊게 검증하면 요청이 폭발하고 시간이 오래 걸린다. 그래서 **"어느 것부터
볼 것인가"**를 정해야 한다. 그게 이 프로젝트의 연구 주제이고, 이 모듈이 그
결정을 내리는 부분이다.

### 1.2 이전에는 어떻게 했나

`scoring/engine.py`가 후보마다 점수를 매겼다. 방식은 **feature에 정해진
가중치를 곱해서 더하는 것**이다.

```text
SQLi 점수 = 20 x status_code_changed
          + 20 x response_length_diff_ratio
          + 35 x sql_error_pattern            -> 0~75점

XSS 점수  = 35 x marker_reflected
          + 10 x response_length_diff_ratio   -> 0~45점
```

여기서 feature는 baseline 응답과 probe 응답을 비교해 얻은 관측값이다. 예를 들어
`sql_error_pattern`은 "probe를 보냈더니 SQL 오류 메시지가 새로 나타났는가"를
0 또는 1로 표시한다.

그리고 SQLi(0~75)와 XSS(0~45)를 함께 줄 세우려고 각자의 최댓값으로 나눴다.

```text
selection_priority = 점수 / 그 유형의 최대 점수
```

### 1.3 무엇이 문제였나

**(가) 가중치의 근거가 없다.** 왜 `sql_error_pattern`이 35점이고
`status_code_changed`가 20점인가? 답할 수 없다. 감으로 정한 값이다.

**(나) 유형 간 비교가 정당화되지 않는다.** SQLi 45점을 75로 나눈 0.6과, XSS
27점을 45로 나눈 0.6이 왜 "같은 정도로 위험"한가? ADR-010 본문도 이걸
"확률이 아니라 selection 전용 key"라고만 적고 넘어갔다.

**(다) 확률이 아니라서 더할 수 없다.** "이 후보를 검증하면 얼마나 이득인가"를
계산하려면 기대값을 더해야 하는데, 임의 스케일의 점수로는 불가능하다.

### 1.4 실제로 측정해보니

이번에 라벨 데이터를 모아 재봤다. 두 가지가 나왔다.

**현행 점수는 상수를 찍는 것보다 나쁘다.**

```text
휴리스틱 점수          Brier 0.2150
"항상 24.66%" 찍기     Brier 0.1858   <- 휴리스틱이 이보다 나쁨
학습한 확률            Brier 0.1134
```

> **Brier score란?** 예측 확률과 실제 정답(0 또는 1)의 제곱 오차 평균이다.
> 낮을수록 좋다. "항상 기저율을 찍는" 무지성 예측기가 기준선이고, 그걸 못
> 이기면 확률로서 가치가 없다는 뜻이다.

즉 휴리스틱 점수는 **순위를 매기는 데는 쓸 수 있어도 확률로는 못 쓴다.**

**손으로 정한 가중치의 부호가 틀렸다.**

```text
학습 결과 (SQLi)
  status_code_changed        = -0.451   <- 휴리스틱은 +20
  response_length_diff_ratio = +4.428
  sql_error_pattern          = +3.770
```

`status_code_changed`가 **음수**로 나왔다. 이유를 보면 납득이 된다 — 입력
검증이 제대로 동작해서 400을 반환하는 것도 상태 코드 변화다. 즉 이 신호는
취약점의 증거이면서 동시에 **방어가 작동한다는 증거**이기도 하다. 사람이
앉아서는 알아내기 어려운 사실이다.

## 2. 용어 정리

앞으로 나올 개념을 미리 짧게 정리한다.

**보정된 확률 (calibrated probability)**
"이 후보가 취약할 확률이 0.7"이라고 말한 것들 중 실제로 약 70%가 취약하면
**보정이 잘 된 것**이다. 단순히 순위만 맞는 점수와 다르다. 확률이어야 서로 다른
취약점 유형의 기대 이득을 더할 수 있다.

**사전분포 (prior)**
데이터를 보기 전의 믿음. 우리는 기존 휴리스틱 가중치를 prior로 썼다. 데이터가
없으면 휴리스틱 그대로 동작하고, 데이터가 쌓이면 그만큼만 움직인다.

**수확 체감 / submodular**
같은 것을 두 번째로 확인할 때의 가치가 첫 번째보다 작은 성질. `/product`
라우트에서 SQLi를 하나 확인했으면 같은 라우트의 다른 파라미터를 또 확인하는
가치는 줄어든다. 같은 코드가 처리하니 결과가 비슷하기 때문이다.

**근사 보장 (approximation guarantee)**
"최적해를 못 찾더라도 최소한 최적해의 몇 %는 보장한다"는 수학적 정리.
`1 - 1/e = 약 0.632`는 "최적의 63.2% 이상은 항상 달성"이라는 뜻이다.

**Conformal (등각) 예측**
"놓치는 비율을 알파 이하로 유지한다"는 보장을 **분포 가정 없이** 주는 방법.
"recall 90%를 보장하는 최소 후보 집합"을 구하는 데 쓴다.

**Recall@K / Precision@K**

- Recall@K: 실제 취약점 중 상위 K개 안에 들어온 비율 (얼마나 안 놓쳤나)
- Precision@K: 상위 K개 중 실제 취약점 비율 (얼마나 헛짚지 않았나)

**MAP@K / NDCG@K**
순위 품질을 하나의 숫자로 요약한 지표. 정답이 위쪽에 몰려 있을수록 높고 1.0이
만점이다.

**out-of-fold (교차검증)**
모델을 평가할 때 **그 데이터를 학습에 쓰지 않은 모델**로 채점하는 것. 자기가
본 답안지로 채점하면 점수가 부풀려지므로 반드시 이렇게 해야 한다. 우리는
애플리케이션 단위로 하나씩 빼면서 평가했다.

## 3. [요청 1] 기존 휴리스틱과 무엇이 다른가

### 3.1 핵심: 휴리스틱을 버리지 않고 흡수했다

가장 중요한 설계 결정이다. 기존 가중치를 **지우지 않고 prior로 바꿔 넣었다.**

```text
prior 평균 = 기존 가중치 / 10
학습 데이터 0개일 때 = logit(기저율) + 기존점수 / 10
```

이게 무슨 뜻이냐면 — **학습 데이터가 하나도 없으면 기존과 정확히 같은 순서가
나온다.** 그래서:

- 코퍼스가 없어도 안전하게 도입할 수 있다 (동작이 안 바뀜)
- 데이터가 쌓이면 근거가 있는 만큼만 움직인다
- 논문에서 **"rule-based는 데이터가 0일 때의 특수해"**라고 쓸 수 있다. 기존
  방식을 부정하는 게 아니라 일반화하는 구조다

### 3.2 바뀌지 않은 것

기존 파이프라인은 **하나도 건드리지 않았다.** `analyze`, `-u`, `RankScore`,
`selection_priority`, `select_top_k()` 전부 그대로다. 결정 계층은 그 검증된
출력을 **소비하는 별도 경로**로 붙어 있다.

```text
vulnspider decide         <- 새로 추가
vulnspider corpus ...     <- 새로 추가
vulnspider analyze ...    <- 변경 없음
vulnspider -u URL         <- 변경 없음
```

### 3.3 비교 요약

| | 기존 | 결정 계층 |
|---|---|---|
| 출력 | 0~75 / 0~45 임의 점수 | 0~1 확률 |
| 유형 간 비교 | 최댓값으로 나눔 (근거 없음) | 확률이라 원리적으로 가능 |
| 가중치 출처 | 사람이 정함 | 코퍼스에서 학습 (휴리스틱이 prior) |
| 불확실성 | 표현 못 함 | 사후 분산으로 표현 |
| 몇 개 뽑나 | 사람이 K 지정 | K + 예산 + recall 보장 |

## 4. [요청 2-A] Scoring 알고리즘 상세

### 4.1 무엇을 하는가

각 후보의 feature를 보고 **취약할 확률**을 낸다. 방법은 **베이지안 로지스틱
회귀**다.

```text
P(취약 | 증거) = sigmoid(w0 + w1*f1 + w2*f2 + ...)
```

`sigmoid`는 임의의 실수를 0~1로 눌러주는 함수다. `w`가 가중치인데 이걸 사람이
정하지 않고 **데이터에서 추정**한다. 다만 완전히 자유롭게 두지 않고 기존
휴리스틱 근처에서 시작하도록 prior를 건다.

의존성은 0개다. `pyproject.toml`이 `dependencies = []`라 numpy도 못 쓰므로
행렬 분해까지 표준 라이브러리로 직접 구현했다.

### 4.2 관측하지 못한 feature 처리

probe가 실패하거나 응답을 디코딩하지 못하면 feature를 **관측하지 못한다.**
이때 0으로 채우면 안 된다 — "확인해보니 없었다"와 "확인을 못 했다"는 완전히
다르기 때문이다(도메인 규칙 8).

로그 오즈 공간에서는 이게 자연스럽게 처리된다. 미관측 feature는 **합에서 그냥
빠진다.** 의미상 "증거 없음 -> 믿음이 그대로 유지됨"이 되어 정확히 맞다.

> **알려진 한계:** 선형 모델에서는 "관측된 0"과 "미관측"이 둘 다 기여 0이라
> 점수상 구분되지 않는다. 상태 자체는 `observed` 플래그로 보존되지만 점수는
> 같다. 구분하려면 feature마다 별도 지시자가 필요하고 그건 지금 코퍼스 규모를
> 넘는다.

### 4.3 확률은 "얼마나 확신하는지"도 반영한다

점수가 같아도 **근거의 튼튼함**이 다를 수 있다. feature 하나에 기댄 0.9와 잘
검증된 feature 네 개에 기댄 0.9는 다르게 취급해야 한다.

이 모델은 가중치의 불확실성까지 적분하므로 **불확실한 가중치에 기댄 점수는
기저율 쪽으로 당겨진다.** 학습이 끝나면 코퍼스가 정밀하게 고정한 가중치는
분산이 작아 덜 당겨지고, 거의 관측되지 않은 가중치는 크게 당겨진다.

기존 휴리스틱과 **정확히 같은 순서**가 필요한 소비자는 `logit_mean`을 읽으면
된다. 예산 배분처럼 기대값을 계산해야 하는 소비자는 `probability`를 쓴다.

### 4.4 실제 데이터가 드러낸 버그

처음 구현은 학습이 **발산**했다. 첫 결과가 절편 +29.8, Brier 0.4598로 상수
예측기보다도 나빴다.

원인은 데이터의 성질이었다. 취약한 XSS 후보 중 `marker_reflected = 0`인 것이
하나도 없어서 그 가중치가 무한대 쪽으로 계속 밀려나갔다. 매 반복이 직전보다 더
크게 빗나가는 상태였다.

해결은 **매 걸음이 반드시 개선되는지 확인하고, 아니면 보폭을 절반으로 줄이는
것**이다.

```text
수정 전:  절편 +29.8,  Brier 0.4598
수정 후:  절편  -4.2,  Brier 0.1134
```

> 이 버그는 손으로 만든 테스트 픽스처로는 재현되지 않았다. **실제 코퍼스를
> 수집했기 때문에** 드러났다. 회귀 테스트를 붙여놨다.

## 5. [요청 2-B] Selection Top-K 알고리즘 상세

### 5.1 무엇을 최대화하는가

확률이 나왔으면 이제 **어느 것들을 고를지** 정해야 한다. 단순히 확률 순으로
K개를 자르면 될 것 같지만 문제가 있다.

같은 라우트(`/product`)의 후보들이 상위를 독차지할 수 있다. 그런데 그것들은
**같은 서버 코드가 처리**하므로 결과가 비슷하다. 하나 확인하면 나머지도 거의
알 수 있는데 예산을 다 써버리는 셈이다.

그래서 목적함수에 **수확 체감**을 넣었다.

```text
가치(S) = 그룹별 합계 [ 1번째 x 1.0 + 2번째 x 0.5 + 3번째 x 0.25 + ... ]
          후보 하나의 가치 = 취약 확률 x 심각도
```

그룹은 endpoint fingerprint로 묶는다. 이렇게 하면 **수확 체감이 탐색에 붙인
꼼수가 아니라 목적함수 자체의 성질**이 되고, 그 덕분에 아래 보장이 성립한다.

### 5.2 보장이 제약에 따라 달라진다

Top-K가 주 파라미터이고 요청 예산은 선택적 보조 제약이다(ADR-027). 어느 것을
쓰느냐에 따라 **알고리즘과 보장이 달라진다.** 정직하게 분리해서 보고한다.

| 활성 제약 | 방식 | 보장 |
|---|---|---|
| Top-K만 | 순수 이득이 큰 순 | `1 - 1/e = 약 0.632` |
| 예산만 | **요청당** 이득이 큰 순 + 최선 단일 후보 | `1/2 x (1 - 1/e) = 약 0.316` |
| 둘 다 | 요청당 이득 + 최선 단일 후보 | **주장하지 않음** |

왜 방식이 달라지냐면 — **비용은 예산이 있을 때만 의미가 있다.** 개수만
제한되면 싼 후보를 우대할 이유가 없고, 그럼에도 요청당 이득으로 정렬하면
`(1 - 1/e)` 보장을 공짜로 잃는다. 그래서 체제별로 정렬 기준을 바꾼다.

**"최선 단일 후보" 비교가 왜 필요한가?** 요청당 이득만 보면 **싼 부스러기로
예산을 채우고 정작 값비싼 대어를 못 사는** 최악의 경우가 생긴다. 그래서 "제일
좋은 후보 하나만 고른 경우"와 비교해 나은 쪽을 택한다. 이 두 번째 팔이 보장을
성립시키는 핵심이다.

둘 다 걸리면 수학적으로 방어 가능한 결합 보장이 없다. **없는 정리를 있다고
적는 대신 값을 비워둔다.**

이론 하한은 느슨하다. 소규모 문제에서 전수 탐색 최적해와 비교하면 실측 평균은
**0.95 이상**이었다.

### 5.3 몇 개를 뽑아야 하는가 — Conformal

K를 사람이 정하는 대신 **목표 recall에서 유도**할 수도 있다.

```text
"놓치는 비율을 10% 이하로 유지하는 가장 작은 집합"
```

이걸 분포 가정 없이 보장하는 게 conformal risk control이다. 보정용
애플리케이션들에서 임계값을 하나 정하면 **처음 보는 애플리케이션에 대해서도**
평균적으로 그 보장이 성립한다.

**정직하게 밝힌 두 제약:**

- 애플리케이션이 충분해야 한다. **recall 90% 보장에는 최소 9개**가 필요하다.
  부족하면 보장을 계산하지 않고 표시만 남긴 뒤 전부 선택한다. **보장되지 않은
  값을 보장된 것처럼 내놓지 않는다.**
- 애플리케이션끼리 교환 가능하다는 가정이 웹에서는 약하다. DVWA와 자체 제작
  Spring 앱은 성격이 다르다. 그래서 하나씩 빼면서 보정하고 실제 위반율을 함께
  보고한다.

보정은 반드시 **out-of-fold 확률**로 한다. 모델이 이미 답을 본 데이터로
보정하면 보장이 낙관적으로 부풀려진다.

## 6. [요청 3] Evaluation Metrics 도입과 검증

### 6.1 왜 필요했나

`EVALUATION_PROTOCOL.md`가 Recall@K / Precision@K / MAP@K / NDCG@K를 핵심
지표로 지정하고 비교군 A/B/C까지 정의해뒀는데, **정작 그걸 계산하는 코드가
없었다.** 알고리즘은 좋아졌는데 프로토콜이 정한 언어로 말할 수단이 없었다.

### 6.2 코드보다 먼저 규칙을 정했다

지표는 정의만으로 계산이 확정되지 않는다. 애매한 지점이 다섯 개 있고, **숫자를
뽑은 뒤에 정하면 유리한 쪽으로 고를 수 있다.** 그래서 문서에 먼저 못박았다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 세는 단위 | 후보 단위 (버그 단위 병기) | 버그 하나가 여러 후보로 부풀지 않도록 |
| 라벨 없는 후보 | 비관련으로 셈 | 제외하면 라벨을 안 달수록 점수가 좋아짐 |
| 평균 단위 | 애플리케이션 1개 = 질의 1개 | 후보 많은 앱이 평균을 지배하지 않도록 |
| 동점 | 기대값으로 계산 | tie-break 순서에 결과가 좌우되지 않도록 |
| K와 예산 | 표를 분리 | 서로 다른 것을 재므로 |

**동점 문제가 실제로 있다.** 한 앱은 후보 10개인데 서로 다른 확률이 8개뿐이다.
동점이 K 경계에 걸치면 순서만으로 Recall@K가 바뀌는데, 현재 tie-break은 후보
id 해시라 **임의**다. 그래서 평가는 "동점 그룹 안에서 무작위 순서를 가정한
기대값"으로 계산한다.

### 6.3 지표 구현이 맞는지 두 겹으로 검증했다

외부 라이브러리를 쓸 수 없으니 sklearn과 대조할 수 없다. 대신:

**(가) 무작위 비교군 항등식.** 무작위 순위는 "전부가 하나의 동점 그룹"인 특수
케이스다. 따라서 기대값 계산이 정확하다면 **Precision@K가 모든 K에서 기저율과
정확히 같아야 한다.**

```text
실측 Precision@K = 0.247  (K=1,3,5,10 전부)
기저율           = 36/146 = 0.2466   OK
```

동점 처리와 무작위 비교군을 **동시에** 검증하는 항등식이다.

**(나) 전수 열거 대조.** 동점 처리 공식이 **모든 순열을 다 세어본 기대값**과
소수점 9자리까지 일치하는지 확인했다(Recall, NDCG, average precision 각각).

## 7. 그 외에 수행한 것

### 7.1 라벨 코퍼스 구축

학습과 보정에는 정답이 붙은 데이터가 필요하다. 안전 규칙상 인터넷 스캔은
불가능하므로 **동작을 직접 작성해서 정답을 아는 로컬 애플리케이션**을 만들어
썼다. DVWA나 WebGoat가 실습용 코퍼스로 쓰이는 것과 같은 근거다.

- 14개 애플리케이션을 시드에서 생성해 127.0.0.1에만 바인딩
- 각각에 **실제 파이프라인**을 실행 (실제 HTTP, 실제 크롤러, 실제 feature 추출)
- 관측된 feature를 정답과 이어붙여 146개 라벨 샘플 수집
- feature 값은 **하나도 합성하지 않았다**

**일부러 어렵게 만들었다.** 분리가 쉬운 데이터는 모델을 실제보다 좋아 보이게
한다. 그래서:

- `safe_validation` 라우트는 숫자가 아닌 입력에 400을 반환한다 -> 상태 코드가
  바뀌므로 **진짜 오탐을 만든다**
- `sqli_blind`은 SQL 오류를 내지 않고 **응답 길이만** 달라진다 ->
  `sql_error_pattern`으로는 절대 못 잡는다
- `xss_escaped`는 마커를 이스케이프해서 반사한다 -> 8.5의 구조적 한계

시드에서 **바이트 단위로 재현된다.** 두 번 돌려서 파일을 비교하면 동일하다.

### 7.2 Value of Information — 만들었지만 켜지 않았다

원래 계획에는 "다음에 어떤 probe를 실행할지 정보 이득으로 정하는" 계층이
있었다. 구현하고 테스트까지 마쳤지만 **CLI에 연결하지 않았다.**

측정해보니 현재 파이프라인에는 결정할 것이 없었기 때문이다:

1. probe 한 쌍이 이미 feature를 **전부** 준다 -> "다음에 뭘 잴까"가 없음
2. 미관측 feature가 **146개 중 0개** -> 다시 재서 알아낼 게 없음
3. 결정 계층이 실행될 땐 이미 probe가 끝나 있음 -> 배분할 probe 예산이 없음
4. 모델에서 후보끼리 독립 -> A를 재도 B가 안 변하므로 **적응적 순서가 임의
   순서보다 나을 수학적 근거가 없음**

지금 연결하면 실행되지 않거나 실행돼도 아무것도 바꾸지 않는 코드가 생긴다.
**없는 기여가 있는 것처럼 보이는 게 더 나쁘다.** 판단 근거를 ADR-026과 모듈
주석에 남겨서 다음 사람이 무심코 연결하지 않도록 했다.

살리려면 배선이 아니라 모델링이 필요하다 — 같은 코드 경로의 후보끼리 정보를
주고받게 하거나 probe 종류를 늘려야 한다. 둘 다 **관측 계층 작업**이지
scoring/selection이 아니다.

### 7.3 Ablation — 왜 확률이어야 하는가

가중치를 다르게 추정하는 단순한 방법(Naive Bayes)과 비교했다.

```text
                 Brier    ECE      Rec@1   Rec@3   MAP@5
Naive Bayes      0.1837   0.1954   0.280   0.625   0.663
로지스틱          0.1134   0.1146   0.405   0.869   0.871
항상 기저율       0.1858     -        -       -       -
```

**Naive Bayes는 확률로는 못 쓰는데(기저율과 거의 동급) 순위는 무작위보다 두 배
이상 낫다.** 순위 지표만 봤다면 "쓸 만하다"고 결론냈을 것이다.

이게 **확률이 필요한 이유를 독립적으로 증명한다.** 예산 배분은 서로 다른
유형의 기대 이득을 실제로 더해야 하므로 순위만 맞는 점수로는 부족하다.

### 8.4 처음 보는 앱 12개에서

**K 제약과 예산 제약은 반드시 표를 나눠서 본다.** 서로 다른 것을 재기 때문에
방법의 순위가 뒤집힐 수 있다.

Top-K 5, 예산 없음:

```text

휴리스틱                33/33 =1.00    60   294
학습 모델               26/33 =0.79    60   312
학습 모델 + conformal    33/33 =1.00    43   204
```

Top-K 5 + 예산 20 요청:

```text
                        recall      검증  요청
휴리스틱                18/33 =0.55    55   213
학습 모델               27/33 =0.82    50   216
학습 모델 + conformal    31/33 =0.94    35   174
```

### 8.5 여기서 나온 가장 중요한 발견

위 표에서 **학습 모델이 휴리스틱보다 나쁜 칸**이 있다(0.79 대 1.00). 숨기지
않고 원인을 밝힌다. 유형별로 쪼개면 손실이 **전부 XSS**다.

```text
휴리스틱   SQLI 25/25   XSS 8/8
학습 모델   SQLI 25/25   XSS 1/8
```

학습 모델은 `P(XSS | 반사됨) = 약 0.41`을 **정확하게** 배웠다. 코퍼스에서
마커가 반사된 34개 중 실제 취약은 14개뿐이기 때문이다.

문제는 **현재 feature로는 그 34개를 서로 구분할 수 없다는 것**이다. 마커가
영숫자(`VULNSPIDER_` + 16진수)라서, 이스케이프해서 출력하는 안전한 앱이나 그냥
출력하는 취약한 앱이나 **똑같이 "반사됨 = 1"**이 된다.

```text
xss_raw      <h2>Results for VULNSPIDER_ABC123<script></h2>          취약
xss_escaped  <p>No matches for VULNSPIDER_ABC123&lt;script&gt;</p>   안전
             둘 다 marker_reflected = 1.0
```

즉 **34개 중 20개는 어떤 알고리즘으로도 걸러낼 수 없는 구조적 오탐**이다.

휴리스틱은 반사를 과신해서(0.81) XSS를 전부 위로 올린다. K가 넉넉하면 그 과신이
공짜라 우연히 recall이 좋아지고, 예산이 조이면 같은 과신이 요청을 낭비해
0.55로 무너진다. **휴리스틱이 옳았던 게 아니라 제약이 느슨해서 틀린 값이
드러나지 않은 것이다.**

conformal 임계값이 이 격차를 메운다. XSS 음성(약 0.065)은 자르고 양성(약
0.46)은 남겨서 **같은 recall을 검증 28%, 요청 31% 적게** 달성한다.

### 8.6 다음 브랜치의 상한

`safe_html_encoding_detected`(이스케이프 여부 탐지)가 구현되면 어디까지 갈 수
있는지 오라클로 측정했다.

```text
                Brier     Rec@1   Rec@3   MAP@5
현재            0.1134    0.405   0.869   0.871
상한            0.0628    0.440   0.964   1.000
```

**MAP@5가 1.000** — 모든 앱에서 모든 정답이 모든 오답 위에 온다. 구조적 오탐
20개가 통째로 사라지기 때문이다.

다만 이 상한은 낙관적이다. 우리 합성 앱은 이스케이프를 일괄 적용하거나 아예 안
하거나 둘 중 하나라 분리가 깔끔하다. 실제 앱은 부분 이스케이프, 문맥별
이스케이프, 문맥에 틀린 이스케이프가 섞인다. 그리고 마커에 위험 문자를 넣으면
**WAF가 걸러서 반사 자체가 안 되는 새로운 미탐**이 생길 수 있다 — 영숫자
마커와 sentinel 마커를 함께 보내 "필터링됨"을 별도 상태로 잡아야 한다.

결정 실행:

```bash
PYTHONPATH=src python -m vulnspider decide --url http://127.0.0.1:PORT/ --top-k 5 --model data/corpus/model.json --conformal data/corpus/conformal.json -o decision.json --html-output decision.html
```

```text
vulnspider: selected 3 of 12 candidates (top-k 5, 12 requests,
            expected findings 1.85, limited by top_k)
```

`decision.json`에 검증 순서, 후보별 확률·비용·심각도, 어느 제약이 걸렸는지,
보장 정보가 들어 있다. `--html-output`을 주면 같은 내용을 브라우저에서 볼 수
있는 리포트가 함께 생긴다 — **URL 하나로 최종 리포트까지 가는 단일 명령**이다.

리포트에는 후보별로 어떤 feature가 관측됐고 각각이 log-odds를 얼마나 움직였는지
표로 나온다. **미관측 feature는 "not observed"로 표시**되어 관측된 0과 구분된다.

### 9.6 기존 HTML 대시보드 (휴리스틱 경로, 변경 없음)

`analyze`는 **기존 휴리스틱 순서**를 렌더링한다. 결정 계층을 쓰지 않는다.

```bash
PYTHONPATH=src python -m vulnspider analyze --url http://127.0.0.1:PORT/ --top-k 10 --output analysis.json --html-output report.html
```

브라우저로 열면 선택된 후보와 실제로 보낸 요청이 보인다.

### 9.7 실제 앱을 쓸 때 (DVWA 등, 향후)

`build_corpus.py`는 합성 앱 전용이다. 실제 앱은 앱별로 수집한다.

```bash
PYTHONPATH=src python -m vulnspider corpus collect --url http://localhost:8080/ --application-id dvwa --ground-truth gt/dvwa.json -o data/corpus/real.jsonl --append
```

```bash
PYTHONPATH=src python -m vulnspider corpus fit --corpus data/corpus/real.jsonl -o model.json --report calibration.json
```

```bash
PYTHONPATH=src python -m vulnspider corpus calibrate --corpus data/corpus/real.jsonl --target-recall 0.85 -o conformal.json
```

**팁:** 빈 정답 파일로 `collect`를 먼저 돌리면 발견된 후보 키를 전부 출력한다.
그 목록이 곧 라벨링 워크시트가 된다.

앱 7개 기준 인증 가능한 최대 recall은 `n/(n+1) = 0.875`이므로 목표를 0.85로
잡는다.

## 10. 명시적 한계

발표나 논문에서 **먼저 밝히고 시작한다.**

| 한계 | 내용 |
|---|---|
| 합성 앱 | DVWA/WebGoat가 아니다. 수치를 실제 앱 성능으로 일반화하면 안 된다 |
| XSS 구조적 오탐 | 반사 34개 중 20개는 현재 feature로 구분 불가 |
| 비용·심각도 | 측정값이 아니라 정책이다. 예산 효율 수치는 이 정책에 조건부다 |
| conformal 가정 | 앱 간 교환 가능성이 약하다. 위반율을 함께 보고해야 한다 |
| 관측된 0 vs 미관측 | 점수상 구분되지 않는다 |

**다음 우선순위**

1. **Feature 확장** — `safe_html_encoding_detected`,
   `dangerous_reflection_context`. 8.6절의 상한이 목표치다. probe 마커에 위험
   문자 sentinel을 넣어야 하므로 **feature 추출만이 아니라 probe planner 변경이
   포함된다.** 스코프 잡을 때 빠뜨리지 말 것
2. **크롤러 인증** — 실제 앱 진입의 유일한 블로커. DVWA/bWAPP 등이 전부 로그인을
   요구한다
3. **실제 앱 코퍼스** — DVWA 파일럿 후 6~7개
4. **전체 재측정** — 이 시점에야 수치가 실제 웹 애플리케이션에 대한 주장이 된다
