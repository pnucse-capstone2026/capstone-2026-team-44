# DemoShop · 결과 대시보드 변경 공유

기준: 2026-09-15 / `feat/dashboard-improve` / 구현 커밋 `eaeb8e4`

웹 보안에 익숙하지 않은 학생·교수가 시연을 따라올 수 있도록 화면과 설명을 개선했다.
이번 공유 작업에서는 **UI를 추가 변경하지 않고 문서 작성과 테스트만 수행했다.**

## 1. DemoShop 변경

- 홈·상품·장바구니·주문 화면을 쇼핑몰 형태로 정리하고, 로컬 상품 사진 4개를 추가했다. 이후 상품만 다시 칠한 변형 사진 8장(`tools/demo_shop_assets/make_variants.py`, 배경·그림자 유지)으로 상품을 12개로 늘려 브랜드·색상·사이즈·정렬·페이지 필터가 실제로 동작한다. 카탈로그·위시리스트의 페이저는 결과가 한 페이지여도 항상 표시된다(`page` 입력점의 화면 대응물).
- 각 경로의 canonical GET 폼이 곧 화면의 UI다. 카탈로그·검색은 상품 목록 위 필터 바, 상품 상세는 옵션 패널(`id`·`variant`·`tab`·`qty`), 장바구니·주문서는 주문 양식, 나머지 경로는 그 서비스의 조회·등록 양식으로 렌더링되고, 버튼 문구도 경로별로 다르다(주문 조회, 문의 보내기 …). 제출한 값은 URL 쿼리에서 읽어 목록 필터·정렬·페이지, 상품 총액, 쿠폰 할인, 배송비 등에 반영되고, 서버의 파라미터별 응답 카드(조회 행, 반사 문구, DB 오류, 검증 경고)는 폼 아래 "조회 응답" 영역에 그대로 보인다.
- 상품 상세의 `variant` 칩은 표시 중인 상품의 옵션으로 바뀐다. 스니커즈는 자기 색의 사이즈(250–280), 토트는 자기 색의 M·L, 헤드폰·램프는 모델의 색 3가지. 상품이 바뀌면 그 상품의 색(사이즈가 있으면 270 / M)이 선택되고, 쿼리 없는 기본 페이지의 `black-270`은 크롤 baseline이라 그대로 둔다.
- 상품 데이터(이름·가격·옵션)는 페이지 HTML이 아니라 별도 스크립트 `/assets/products.js`로 내려간다. 순위는 응답 바이트에 민감하므로(같은 타깃이면 결정적이지만, HTML이 몇 KB만 달라져도 확률이 소수점 셋째 자리에서 움직여 근소한 순위가 바뀐다) 상품·옵션·CSS·JS를 고쳐도 라우트 HTML이 바뀌지 않게 해 두었다. 이 상태에서 스캔을 두 번 돌리면 결과가 동일함을 확인했다.
- 빠른 선택 칩·페이저·탭 버튼은 이름 없는 `type="button"`이다. 입력 이름·기본값·폼 action·응답 동작·정답 데이터는 그대로이고, 크롤 결과도 33개 엔드포인트·100개 입력점으로 같다. 단, 페이지 HTML이 커져 응답 크기 기준선이 바뀌므로 과거 순위 지표와 수치를 그대로 비교하면 안 된다(`tools/demo_shop_assets/README.md` 참고).
- 기존 공개 영역 **32개 경로, 100개 query 입력점**을 유지한다. 정답 구성은 취약 40개·안전 60개이며, 인증 영역의 3개 경로는 별도다.
- 기존 입력 이름·기본값·GET 폼·응답 동작·정답 데이터와 인증 동작을 유지한다.
- 입력점에 작은 표식을 붙였다. 마우스 올림·키보드 포커스로 **#001–#100, 항목 이름, 파라미터, 요청 형태(`GET /search?q=…`)**를 확인한다. 숨김 입력에도 안내 표식이 있다.
- 우측 하단 **⊙ 입력점 표시** 버튼으로 시연용 표시 모드를 켠다. 100개 입력 컨트롤에 진한 외곽선과 번호가 붙고, 헤더 검색창·카테고리 탭·상품 목록·상품 탭·페이저처럼 입력점으로 이어지는 화면 요소에는 점선 외곽선과 `⊙ #001 검색어 q` 태그가 붙고, 빠른 선택 칩과 페이지 버튼도 녹색으로 바뀐다. 설정은 브라우저 `localStorage`에 남아 페이지를 이동해도 유지된다.
- 헤더 검색창은 실제로 동작한다. Enter 또는 돋보기를 누르면 `/search?q=검색어`로 이동해 상품 목록이 걸러지고, 입력점 #001이 검색어를 그대로 되돌려 준다. 검색창은 `name`도 `<form>`도 없어 크롤 표면은 기존 `/search` GET 폼 그대로다.
- 번호는 DemoShop의 작성 순서에 따른 안내 번호다. 분석기의 InputPoint ID나 후보 순위와 다르다.
- 구매 화면은 시연용이며 실제 주문·결제·배송을 처리하지 않는다.

구현: [demo_shop.py](../tools/demo_shop.py), [demo_shop_storefront.py](../tools/demo_shop_storefront.py)

## 2. 리포트 대시보드 변경

| 영역 | 구현된 내용 |
| --- | --- |
| 공통 | 붉은 도트 거미 로고, ‘웹사이트 취약점 분석 결과 개요’ 제목, 메뉴·검색·필터·화면별 인쇄 |
| 화면 이동 | HTML 한 파일 안에서 분석 개요 / 후보 목록 / 후보별 상세 / 리포트 읽는 법으로 이동 |
| 분석 과정 | 엔드포인트 수·입력점 수·유형별 후보 수·선택된 후보 수를 단계로 연결 |
| 시각화 | 경로와 입력점의 소속 지도, 후보 유형 구성 차트, 최종 신뢰도 순 대표 후보 최대 3개의 검증 전후 비교 |
| 이름·번호 | 해당 후보의 저장된 baseline 응답에서 확인한 DemoShop 이름·번호를 지도·목록·비교·상세에 표시 |
| 후보 상세 | 초기 관찰 근거, baseline/probe 요청 정보와 상태·크기, 추가 검증 페이로드·결과·실행 출처, 방어 지침 |

**표시 원칙**

- ‘상위 취약점 후보’, ‘최종 신뢰도’ 용어를 사용한다. 추가 검증이 없으면 검증 전 확률을 최종 신뢰도로 그대로 표시한다.
- 검증 전 확률과 검증 후 최종 신뢰도는 분석기가 제공한 값을 사용한다. 리포트에서 점수를 새로 계산하지 않는다.
- 같은 입력점의 여러 유형은 대표 유형으로 묶어 표시한다. **선택된 유형별 후보 수와 화면의 대표 후보 수는 다를 수 있다.**
- 이름·번호의 출처가 없거나 중복·불일치하면 원래 경로와 입력점 이름을 유지한다. 정답 데이터에서 이름이나 취약성 정보를 가져오지 않는다.
- 지도 선은 소속 관계다. 실제 이동 경로나 공격 경로를 뜻하지 않는다. 후보 수·신뢰도는 취약점 확정이나 사이트 전체의 안전 등급이 아니다.
- 외부 라이브러리·폰트·이미지 요청 없이 HTML 파일 자체로 열리며, 원문 데이터는 이스케이프한다.

## 3. 현재 한계와 다음 소규모 개선 제안 — 미구현

**우선 1: 후보 상세의 응답 비교 카드**

baseline(일반 입력)과 probe(입력 하나를 변경)의 응답을 좌우로 놓고,
상태·본문 크기와 함께 관련 본문 일부를 보여준다. 예를 들어 보낸 표식이
응답에 나타난 위치, 인코딩된 형태, DB 오류 문구를 강조하면 관찰 근거를 설명하기 쉽다.
현재는 요청 URL·주입값·상태·크기를 표시하며, **응답 본문 발췌·차이 강조는 없다.**
추가한다면 실제 저장된 응답만 사용하고, HTML은 실행하지 않는 텍스트로 표시한다.
민감한 값은 가리고, 본문이 없으면 ‘응답 본문 미제공’으로 남긴다.

**우선 2: Feature 값 옆에 짧은 해석 붙이기**

기존에도 Feature의 한국어 설명과 실제 기여도 부호에 따른 확률 상승·하락 방향이 있다.
여기에 `실제 값 / 관찰 의미 / 이번 후보 점수에 미친 방향`을 가까이 배치하면 좋다.

- `response_length_diff_ratio`: 입력 변경 뒤 응답 크기가 달라진 정도다. 정상적인 검색 결과 변화도 원인이므로 **값이 크다고 XSS 확률이 반드시 올라가지는 않는다.** 이번 모델의 실제 기여도가 양수인 경우에만 확률을 높이는 방향으로 설명한다.
- `marker_reflected`: 보낸 표식이 응답에 나타난 관찰이다. 반사만으로 JavaScript 실행이나 XSS를 확정할 수 없다.
- `safe_html_encoding_detected`: 특수 문자의 안전한 인코딩 여부를 관찰한다. 실제 관측값과 모델 기여도에 맞춰 해석하고, 미관측은 0으로 취급하지 않는다.

여기서 Feature의 모델 기여도는 주로 **검증 전 확률의 근거**다.
추가 검증으로 바뀐 최종 신뢰도는 별도의 검증 신호·규칙으로 설명해야 한다.

**우선 3: 개요의 ‘상위 후보 주요 신호’ 요약표**

대표 후보 5개 정도를 행으로, 입력값 반사·인코딩·응답 변화 등의 신호를 열로 놓고
관측값과 미관측을 구분한다. 클릭하면 해당 상세 화면으로 이동한다.
새로운 보안 점수나 거대한 그래프 없이도 후보 사이의 차이가 눈에 들어온다.
본문 비교 카드를 먼저 완성하고 남는 시간에 적용하는 것을 권장한다.

## 5. 팀원이 DemoShop을 직접 열 때

별도 터미널에서 저장소 루트 기준으로 실행한다. 아래는 재현 안내이며 이번 테스트 명령과는 구분된다.

```powershell
$env:PYTHONPATH = 'src'
python -B demo_target_server.py --port 8899
```

접속: `http://127.0.0.1:8899/` / 종료: 해당 터미널에서 `Ctrl+C`.
자동 테스트는 이 서버를 미리 실행할 필요가 없다.

## 6. 미리보기와 실제 리포트 구분

- `build/report-preview/story-preview.html`: 최신 UI를 확인하는 **예시 데이터**. 실제 분석 결과로 발표하면 안 된다.
- `build/report-preview/dashboard.html`: 이전 실제 스캔 리포트. 최신 분석 과정·비교 카드 변경까지 반영된 파일은 아니다.
- 최신 UI를 적용한 실제 DemoShop 재스캔 리포트 생성은 아직 확인하지 못했다. 이전 생성 시도가 실행 정책으로 차단되었다.
- `build/` 미리보기·로그는 Git 공유 대상이 아니다. 팀원은 브랜치의 소스와 이 문서를 확인하고, 실제 발표에는 새로 생성한 분석 리포트를 사용해야 한다.
