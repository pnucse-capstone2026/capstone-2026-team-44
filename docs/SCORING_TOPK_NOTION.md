# 취약점 후보 스코어링 & Top‑K 선택 알고리즘 (팀 공유용)

> 졸업과제: **입력점 기반 웹 취약점 후보 우선순위화 및 선택적 검증 알고리즘**
> 이 문서는 `feat/scoring` 브랜치에서 **점수 매기기(Scoring)와 최종 선택(Selection Top‑K)** 을
> 어떻게 바꿨는지, **왜** 바꿨는지, 그리고 **앞으로 무엇을 할지**를 팀원 누구나 읽을 수 있게
> 정리한 문서다. 머신러닝 배경이 없어도 이해되도록 개념부터 설명한다.

---

## 0. 30초 요약

우리가 한 일을 한 문장으로:

> **손으로 정한 임의의 가중치 대신, 정답이 붙은 데이터(코퍼스)에 맞춰 로지스틱 회귀로 가중치를
> 학습한다. 그 결과 점수가 "취약할 확률(0~100%)"이 되고, 확률이 가장 높은 K개의 후보를
> 골라서 보고한다.**

| | 이전 (Rule‑based) | 이후 (이 브랜치) |
|---|---|---|
| 점수를 만드는 법 | 사람이 정한 가중치의 **가중합** | 데이터로 학습한 **로지스틱 회귀** |
| 점수의 의미 | 임의 스케일 (SQLi 0~75, XSS 0~45) | **확률** `P(취약 \| 관측)` — 0~1, 유형 무관 동일 의미 |
| 가중치 근거 | "왜 20점인가?" 답 없음 | 코퍼스에서 추정 — 부호·크기가 데이터로 검증됨 |
| 유형 간 비교 | 각자 최댓값으로 나눔 (정당화 안 됨) | 같은 확률 스케일 (검증 가능) |
| 최종 선택 | 정규화 점수 Top‑K | 확률 Top‑K (**기댓값 관점에서 최적**) |
| 성능 근거 | 없음 | Recall@K / NDCG@K + 비교군 4종 + 캘리브레이션 |

## 1. 우리가 푸는 문제

크롤러가 웹사이트를 훑으면 **검사할 후보가 수십~수백 개** 나온다.

- **입력점(Input Point):** 사용자 입력이 들어가는 지점. 예: `GET /product?id=` 의 `id` 파라미터.
- **후보(Candidate):** `(입력점, 취약점 유형)` 한 쌍. 입력점 하나에서 여러 유형을 의심할 수 있다.

```text
GET /product?id=   에 SQL Injection 이 있는가?   ← 후보 1
GET /product?id=   에 Reflected XSS 가 있는가?   ← 후보 2
GET /search?q=     에 SQL Injection 이 있는가?   ← 후보 3
...
```

후보를 전부 깊게 검증하면 요청이 폭발하고 오래 걸린다. 그래서 **"어느 것부터 볼 것인가"** 를
정해야 한다. 이 **우선순위화**가 졸업과제의 핵심이고, 이 문서가 다루는 부분이다.

우리가 매기려는 값을 **"취약도"** 라고 부른다. 취약도란 곧 **"이 후보가 실제로 취약할
가능성"** 이다. 이걸 잘 계산해서 높은 것부터 K개를 골라 보고하는 것이 목표다.

## 2. 이전 방식 — 휴리스틱 가중합 (그리고 무엇이 문제였나)

### 2.1 어떻게 동작했나

각 feature(관측된 신호)에 사람이 **점수(가중치)** 를 미리 정해두고 곱해서 더했다.
(feature는 baseline 응답과 probe 응답을 비교해 얻은 관측값. 예: `sql_error_pattern` =
"probe를 보냈더니 SQL 오류 메시지가 새로 나타났는가" → 0 또는 1)

```text
SQLi 점수 = 20 × status_code_changed          (상태코드가 바뀌었나)
          + 20 × response_length_diff_ratio    (응답 길이가 달라졌나)
          + 35 × sql_error_pattern             (SQL 오류가 나타났나)     → 0~75점

XSS 점수  = 35 × marker_reflected              (넣은 마커가 반사됐나)
          + 10 × response_length_diff_ratio                              → 0~45점
```

그리고 SQLi(0~75)와 XSS(0~45)를 함께 줄 세우려고 **각자의 최댓값으로 나눴다.**

```text
선택 우선순위 = 점수 ÷ 그 유형의 최대 점수     (예: SQLi 45점 → 45/75 = 0.6)
```

### 2.2 세 가지 문제

**(가) 가중치의 근거가 없다.**
왜 `sql_error_pattern`은 35점이고 `status_code_changed`는 20점인가? 답할 수 없다. 감으로 정한
값이다. 졸업과제에서 "이 숫자는 왜 이 값입니까?"라는 질문에 방어할 수 없다.

**(나) 유형 간 비교가 정당화되지 않는다.**
SQLi 45점을 75로 나눈 `0.6`과, XSS 27점을 45로 나눈 `0.6`이 왜 "같은 정도로 위험"한가?
최댓값으로 나누는 것은 **계산 편의**일 뿐, `0.6`이라는 값이 두 유형에서 같은 의미라는 근거가
전혀 없다.

**(다) 확률이 아니라서 더할 수 없다.**
"이 후보를 검증하면 얼마나 이득인가"를 계산하려면 값을 더해야 하는데, 임의 스케일의 점수는
더해도 의미가 없다. (이게 나중에 Top‑K 최적성과 연결된다 → §5)

### 2.3 실제로 측정해보니 — 상수보다 나빴다

라벨 데이터를 모아 재보니, 휴리스틱 점수는 **"그냥 평균값(상수)을 찍는 것보다도 못했다."**

| 방식 | Brier score (낮을수록 좋음) |
|---|---|
| 항상 평균 취약률(0.15)만 답하기 | **0.186** |
| 휴리스틱 가중합 | 0.194 ← 상수보다 **나쁨** |
| 학습한 로지스틱 회귀 | **0.133** ← 확실히 좋음 |

> Brier score = 예측 확률과 실제(0/1)의 제곱오차 평균. "예측이 정답에서 얼마나 벗어났나"를
> 재는 지표다. 휴리스틱이 상수보다 나쁘다는 건, 손으로 정한 가중치가 오히려 잘못된 자신감을
> 준다는 뜻이다.

## 3. 새 방식 — 코퍼스로 학습한 로지스틱 회귀 (핵심)

여기가 이 브랜치의 심장이다. **"임의 가중치 → 데이터로 학습한 가중치 → 확률"** 로 바꾼다.

### 3.1 코퍼스가 뭔가 — 정답이 붙은 데이터

**코퍼스(corpus)** 는 **"관측된 feature + 정답 라벨"** 이 짝지어진 학습 데이터다.

정답은 아무 사이트에서나 알 수 없다. 그래서 우리가 **취약점을 일부러 심은 작은 웹앱 14개를
로컬(127.0.0.1)에 직접 띄운다**(`tools/corpus_target_site.py`). DVWA·WebGoat가 "실습용으로
일부러 취약하게 만든 앱"인 것과 같은 원리다. 내가 심었으니 정답을 안다.

그다음 그 앱들에 **진짜 크롤러·probe·feature 추출 파이프라인을 그대로 돌려서**(`build_corpus.py`)
관측 feature를 얻고, 저작해둔 정답과 합쳐 `corpus.jsonl`에 쌓는다. **feature 값은 합성하지
않는다 — 실제 HTTP 응답을 비교한 실측값이다.**

코퍼스 한 줄 예시(app00의 `/report` 입력점):

```json
{ "application_id": "app00", "canonical_path": "/report",
  "vulnerability_type": "SQLI",
  "features": { "marker_reflected": 1.0, "response_length_diff_ratio": 0.076,
                "sql_error_pattern": 1.0, "status_code_changed": 1.0 },
  "vulnerable": true }      ← 정답 라벨
```

현재 코퍼스: **앱 14개 · 후보 146개 · 실제 취약 36개** (SQLi 73개 중 22개 취약, XSS 73개 중
14개 취약). 입력점 하나당 후보 2개(SQLi·XSS)가 생긴다.

### 3.2 로지스틱 회귀가 뭔가 — 아주 친절하게

우리가 원하는 건 **확률** `P(취약 | feature)`, 즉 0~1 사이 값이다. 그런데 가중합은 아무 숫자나
(0~75) 될 수 있어서 확률이 아니다. 이 간극을 메우는 게 로지스틱 회귀다. 3단계로 생각하면 된다.

**① 증거를 더한다 (로그오즈, logit).**
각 feature가 "취약 쪽으로 얼마나 밀어주는지"를 가중치로 정하고 더한다. 이 합을 `z`라 하자.

```text
z = β0 + β1·f1 + β2·f2 + ...      (β = 가중치, f = feature 값)
```

`z`는 −∞ ~ +∞ 아무 값이나 될 수 있다. 이 공간을 **로그오즈(log‑odds)** 라 부른다.

**② 확률로 변환한다 (시그모이드, sigmoid).**
`z`를 0~1로 눌러주는 S자 함수 `σ`에 통과시킨다.

```text
P(취약) = σ(z) = 1 / (1 + e^(−z))
```

`z`가 크면 P는 1에 가깝고, `z`가 작으면(음수) 0에 가깝다. `z=0`이면 P=0.5.
**이 시그모이드가 바로 "정규화"다.** 이전에는 점수를 그 유형의 최댓값으로 나눠서(÷max) 억지로
0~1로 만들었지만, 이제는 시그모이드가 **어떤 점수든 확률이라는 하나의 의미 있는 스케일로**
변환한다. 우리가 말한 "로지스틱 회귀를 통한 정규화"가 이 부분이다.

**③ 가중치를 데이터가 정한다 (학습).**
`β`(가중치)를 사람이 정하지 않는다. **코퍼스의 정답과 모델의 예측이 최대한 일치하도록** `β`를
찾는다(최대우도 추정). 즉 "이 feature가 실제로 취약과 얼마나 같이 나타났는가"를 데이터가 계산해
준다. **바로 이 지점에서 '임의의 가중치'가 '데이터가 정한 가중치'로 바뀐다.**

### 3.3 실제로 학습된 결과 (숫자로 보기)

코퍼스로 fit한 SQLi 모델(`data/corpus/model.json`):

```text
z(SQLi) = −1.51
        + (−0.50) × status_code_changed
        + ( 3.94) × response_length_diff_ratio
        + ( 4.41) × sql_error_pattern
P(취약) = σ(z)
```

이 모델로 실제 후보 3개를 계산하면:

| 입력점 | status | len | sqlerr | z | **P(취약)** | 정답 |
|---|---|---|---|---|---|---|
| `/report?report_id` (SQL 오류) | 1 | 0.076 | 1 | +2.69 | **0.94** | True ✅ |
| `/article?article_id` (안전) | 0 | 0.013 | 0 | −1.46 | **0.19** | False ✅ |
| blind SQLi (길이 신호만) | 0 | 0.275 | 0 | −0.43 | **0.39** | True ⚠️ |

앞의 둘은 확률이 정답과 잘 맞는다. 셋째(blind SQLi)는 **일부러 어렵게 만든 경우**다 — SQL 오류도
상태 변화도 없이 길이 차이만 있어서 모델도 39%로 확신하지 못한다. 이렇게 **모델이 틀리거나
망설이는 경우가 코퍼스에 남아 있는 것**이 정직한 데이터의 핵심이다(코퍼스 분리성 수정, §8 참고).
점수가 "94% 취약", "39%로 불확실" 처럼 **바로 해석되는 확률**이라는 점은 그대로다.

## 4. 왜 이게 이전의 문제를 해결하는가 (문제별로 하나씩)

### 문제 (가) "가중치 근거 없음" → 데이터가 근거다

가중치 `β`는 이제 감이 아니라 **데이터에서 추정한 값**이라 부호·크기를 검증할 수 있다.
가장 좋은 예가 `status_code_changed`다.

- **휴리스틱:** +20점 ("상태코드가 바뀌면 SQLi 의심 ↑")
- **학습 결과:** **−0.50** (약한 **음의** 신호)

왜 뒤집혔나? 우리 코퍼스에는 `SAFE_VALIDATION` 이라는 **안전한** 라우트가 있는데, 비정상 입력에
`400`을 돌려주면서 상태코드를 바꾼다. 즉 **"상태코드 변화" 단독은 SQLi의 증거가 아니다** — 안전한
검증 로직도 똑같이 상태코드를 바꾸기 때문이다. 데이터는 이걸 정확히 잡아내서 그 가중치를
음수로 눌렀다.

> **이게 졸업과제의 강력한 서사다:** "손으로 고른 가중치를 데이터가 반박했고, 그 혼동의
> 출처(안전한 검증 로직)까지 설명된다." 이런 주장은 rule‑based 방식으로는 절대 할 수 없다.
> 계수표(β와 그 부호)를 그대로 논문 Table로 쓰면 된다.

### 문제 (나) "유형 간 비교 부당" → 확률은 공통 언어다

확률은 `[0, 1]`에서 **유형과 무관하게 같은 의미**를 가진다: "이런 feature 패턴을 가진 후보 중
실제로 취약했던 비율". 그래서 캘리브레이션이 잘 된 `0.6`은 SQLi든 XSS든 **같은 0.6**이다.
`45/75`와 `27/45`를 비교하던 것과는 근본이 다르다.

그리고 이건 **주장이 아니라 검증**할 수 있다. **신뢰도 곡선(reliability diagram)** 으로
"0.6이라고 예측한 후보들이 실제로 60% 취약했는가"를 그려 확인한다. 측정 결과 캘리브레이션 오차
(ECE)가 휴리스틱 0.210 → 학습 모델 **0.091**로 크게 줄었다.

> (심화, 앞으로 강화할 부분) 유형별로 가중치가 정말 달라야 하는지를 **통계적으로** 보이려면
> "family 상호작용"을 넣은 단일 모델로 검정할 수 있다. 지금은 유형별 모델을 따로 학습하고
> 신뢰도 곡선으로 확인하는 단계이고, 이 검정은 §7 로드맵에 있다.

### 문제 (다) "못 더한다" → 확률은 더할 수 있고, 그래서 Top‑K가 최적이 된다

확률은 기댓값으로 더해진다. 이게 다음 절(§5)의 Top‑K 최적성의 근거가 된다.

## 5. 최종 선택 — 확률 Top‑K (argmax)

점수가 확률이 되면, 최종 선택은 놀랄 만큼 단순해진다.

> **취약 확률이 가장 높은 K개의 후보를 고른다. 끝.**

그리고 이게 **정확한 최적해**다. 이유(한 줄 증명):

- 우리가 최대화하려는 것은 "보여준 K개 중 **실제로 취약한 후보의 기대 개수**"다.
- 기댓값의 선형성에 의해, 그 기대 개수 = 고른 후보들의 **확률의 합**이다.
- 확률의 합을 K개로 최대화하려면 → **큰 확률 K개를 고르면 된다.** (더 이상 뭘 할 필요가 없다.)

이게 §2.2의 문제 (다)와 연결된다. 이전 점수는 임의 스케일이라 "합"이 무의미했지만, 확률은 합이
곧 기대 발견 개수라서 **정렬 한 번이 곧 최적**이 된다. 그래서 우리는 화려한 최적화를 붙이지
않는다 — 붙일 필요가 없다(오히려 실측에서 손해였다, §7).

**동점 처리(tie‑break):** 확률이 같으면 현재는 유형 순서 → 후보 ID 순으로 끊는다. (이 부분은
"심각도(severity)나 검증 비용 기준"으로 바꾸는 것을 §7에서 다룬다.)

**보고:** 후보는 `(입력점, 유형)` 쌍이므로, Top‑K 후보를 입력점 기준으로 묶어 "이 입력점을
이 유형으로 먼저 보라"는 리포트로 낸다.

## 6. 우리가 실제로 좋아졌음을 어떻게 보였나 (평가)

숫자 없이 "좋아졌다"고 하면 졸업과제가 아니다. 그래서 평가 체계를 갖췄다.

- **데이터 분리:** 학습/평가를 **앱 단위(group)로 분리**해 같은 앱이 양쪽에 안 들어가게 한다
  (데이터 누수 방지).
- **비교군 4종:** ① 랜덤 ② 반사만 보는 단순 규칙 ③ 휴리스틱 가중합 ④ 우리(학습 확률).
- **지표:** Recall@K(상위 K에 실제 취약이 얼마나 포함됐나), Precision@K, NDCG@K 등.

**Recall@K (상위 K개 안에 실제 취약을 얼마나 건졌나 — 높을수록 좋음):**

| 방식 | @1 | @3 | @5 |
|---|---|---|---|
| 랜덤 | 0.10 | 0.30 | 0.51 |
| 반사만 보는 규칙 | 0.12 | 0.36 | 0.59 |
| 휴리스틱 가중합 | 0.16 | 0.56 | 0.86 |
| **학습 확률 (우리)** | **0.35** | **0.74** | **0.92** |

**Precision@1 (맨 위 1개가 실제 취약일 확률):** 휴리스틱 0.43 → **우리 0.79.**
**NDCG@5 (순위 품질):** 휴리스틱 0.65 → **우리 0.84.**

세 지표 모두에서 학습 확률이 휴리스틱을 확실히 앞선다. 이 수치는 **코퍼스 분리성을 고친
뒤의 정직한 값**이라, 이전(부풀려진) 값보다 낮지만 그만큼 방어 가능하다. (원본:
`data/corpus/ranking-report.json`, `calibration-report.json`)

## 7. 범위 결정 — 무엇을 빼고, 무엇을 남기나

이 브랜치에는 실험적으로 만든 무거운 모듈들이 있는데, **기본 Top‑K 질문과는 다른 질문에
답하는 것들**이라 **빼거나 축소**한다. 팀 공유의 결론은 **"Scoring + Top‑K 선택"** 하나로
깔끔하게 좁히는 것이다.

| 모듈 | 결정 | 이유 |
|---|---|---|
| 학습된 확률 스코어링 | **유지 (핵심)** | 문제 (가)(나)(다)를 직접 해결 |
| 확률 Top‑K argmax | **유지 (핵심)** | 기댓값 관점에서 최적, 정렬 한 번 |
| 평가 체계 (지표+비교군) | **유지** | "좋아졌다"의 근거 |
| Submodular / Knapsack 예산 선택 | **분리/축소** | "요청 예산 대비 발견 최대화"는 **다른 질문**. 기본 Top‑K와 섞으면 초점이 흐려짐 |
| VoI (순차 probe 선택) | **future work** | 현재는 probe 1회가 feature를 전부 가져와 "다음에 뭘 볼까" 결정할 게 없음 |
| Bayesian 사후분산(불확실성) | **축소** | feature가 4개뿐이라 순위를 바꾸지 않음. 예산·탐색을 다룰 때만 의미 |

> 요컨대 **핵심(확률화 + Top‑K)은 남기고**, 예산·탐색·불확실성 쪽 무거운 장치는 "다른 질문에
> 대한 후속 연구"로 명확히 분리한다. 이렇게 해야 발표에서 "왜 이 복잡한 게 필요하냐"는 질문에
> 방어할 필요가 없어진다.

## 8. 앞으로 할 일 (구현/개선 로드맵)

우선순위 순서(효과 대비 방어력):

1. **코퍼스 분리성 고치기 (✅ 완료).**
   이전 합성 코퍼스는 `response_length_diff_ratio` **한 feature만으로 라벨이 거의 완벽히
   갈렸다**(단일 임계값 정확도 1.00). 저작 단계(`corpus_target_site.py`)에서 (a) 라우트마다
   재현 가능한 랜덤 크기의 정적 chrome을 붙여 길이 비율의 분모를 흔들고, (b) 모든 응답에
   값 의존적 benign 결과 행을 넣어 **안전한 페이지도 입력에 따라 길이가 변하게** 했다. 결과:
   길이 단독 임계값 정확도가 SQLi 1.00→**0.75**, XSS 1.00→**0.81**(다수결 기준선과 동일)로
   떨어져, 판별력이 SQL 오류·상태·반사 feature로 이동했다. 위 §2·§6 수치는 **이 정직한
   데이터로 다시 뽑은 값**이다.

2. **매직 넘버 제거 — 정규화 세기를 CV로 선택.**
   현재 학습에는 사람이 정한 상수(prior 관련 하이퍼파라미터)가 남아 있는데, 이건 "왜 20점?"을
   "왜 이 상수?"로 옮긴 것과 같다. **앱 단위 교차검증으로 이 값을 데이터가 고르게** 하면
   "매직 넘버가 하나도 없다"가 성립한다.

3. **유형 간 비교를 통계로 승격 (family 상호작용 + 검정).**
   유형별 별도 모델 대신, family 상호작용을 넣은 **단일 모델**로 학습하고 우도비 검정으로
   "SQLi와 XSS가 정말 다른 가중치를 필요로 하는가"에 **p‑value로** 답한다. → 문제 (나)의 결정판.

4. **외부 코퍼스로 검증.**
   합성 앱뿐 아니라 DVWA·WebGoat 같은 **실제 취약 앱**으로 held‑out 검증을 붙인다.
   ("합성으로 학습, 실제로 검증" — 발표 방어력이 크다.)

5. **feature 확장.**
   현재 4개 feature로는 "이스케이프된 반사(XSS_ESCAPED, 안전)"와 "생 반사(XSS_RAW, 취약)"를
   구별하지 못한다. `safe_html_encoding_detected` 같은 feature를 추가해 이 한계를 해소한다.

6. **동점 처리 근거화.**
   Top‑K 동점을 유형 순서 대신 **문서화된 심각도(CVSS 기반)나 검증 비용**으로 끊어, 남아 있는
   임의성을 제거한다.

## 9. 용어집

| 용어 | 뜻 |
|---|---|
| **입력점 (Input Point)** | 사용자 입력이 들어가는 지점 (예: `?id=` 파라미터) |
| **후보 (Candidate)** | `(입력점, 취약점 유형)` 한 쌍. 우선순위를 매기는 단위 |
| **feature** | baseline 응답과 probe 응답을 비교해 얻은 관측 신호 (예: SQL 오류 출현 여부) |
| **취약도** | 그 후보가 실제로 취약할 확률 `P(취약 \| feature)` |
| **코퍼스 (corpus)** | "관측 feature + 정답 라벨" 짝으로 이뤄진 학습/평가 데이터 |
| **ground truth** | 각 후보의 정답(취약 True/False) 라벨 |
| **로지스틱 회귀** | 가중합을 시그모이드로 확률로 바꾸고, 가중치를 데이터로 학습하는 모델 |
| **logit / 시그모이드** | logit = 증거의 가중합(−∞~∞), 시그모이드 = 그걸 0~1 확률로 누르는 S자 함수 |
| **캘리브레이션** | "70%라고 한 것들이 실제 70% 취약했는가"의 일치 정도. Brier·ECE로 잼 |
| **Recall@K** | 상위 K개 안에 실제 취약 후보가 얼마나 포함됐나 |
| **Top‑K / argmax** | 값이 가장 큰 K개를 고르는 것 |
